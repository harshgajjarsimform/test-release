Two manual GitHub Actions workflows were built, wired to real GitHub Environment approval gates, and exercised with live gh workflow run dispatches — including deliberately trying to break them — in a sandbox repo before this pattern goes into any real service.

Self-review: intentionally allowed

Only 1–2 people run this pipeline, so prevent_self_review is set to false on all three environments. This does not make runs execute automatically — every run still lands in "Waiting" and needs an explicit Approve click — it just means the same person who triggered it is allowed to be the one who approves it.

Final workflow files

.github/workflows/release.yml

on:
  workflow_dispatch:
    inputs:
      version:
        description: "Version to release, e.g. v1.2.3"
        required: true
        type: string

jobs:
  validate:
    steps:
      - Validate version format (vX.Y.Z)
      - Validate tag does not already exist
      - Validate version is the next allowed increment (patch/minor/major only)
      - Validate dispatched ref is the current tip of main

  release:
    needs: validate
    environment: release-approval
    steps:
      - Create and push Git tag
      - Create GitHub Release
      - Build (simulated)
      - Summary

.github/workflows/deploy.yml

on:
  workflow_dispatch:
    inputs:
      region:
        description: "Target region"
        required: true
        type: choice
        options: [US, EU]

jobs:
  verify:
    steps:
      - Confirm this run was dispatched from a release tag (github.ref_type == 'tag')
      - Confirm a GitHub Release exists for this tag (github.ref_name)

  deploy:
    needs: verify
    environment: "production-${{ inputs.region == 'US' && 'us' || 'eu' }}"
    steps:
      - Deploy (simulated) — real version swaps this step for:
          az login / az aks get-credentials / sed image tag / kubectl apply
      - Summary

What's still simulated (by design, for this sandbox)

  • No Docker build/push — the "Build (simulated)" step just echoes the commands.
  • No real cluster — the "Deploy (simulated)" step echoes the az/kubectl commands instead of running them.
  • Single reviewer — self-review is allowed because there's no second collaborator on this personal repo; a real team repo would size this to how many actual release managers exist.
